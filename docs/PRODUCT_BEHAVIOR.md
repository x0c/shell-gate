# Product behavior

Current standalone configuration and deployment requirements are defined in [standalone design](design/standalone-open-source.md) and [deployment](DEPLOYMENT.md). Historical fleet names below are illustrative roles, not required services. Preserve these established terminal and interaction constraints.


- **多上游机器（2026-08-27 上线）**：支持反代多台终端主机。配置用 `SHELL_TTYD_TARGETS`（逗号分隔的 `名称=地址`，如 `linux=http://terminal.example.com:7681,tokyo=http://extra-terminal.example.com:7681`；列表第一台是默认机器），未配置时回退旧的单值 `SHELL_TTYD_URL`（机器名 `default`）--单机部署不改环境变量升级后行为不变。机器名拼错/重复/非法直接启动失败（fail-fast）。每台机器独立持有反代与网络监控器（一台探测超时不拖累另一台转发）。机器目录由服务端经 `GET /api/machines` 下发（含健康态），客户端不内置机器名。Tab 开在哪台机器上由「预置绑定 > 请求指定 > 默认机器」解析（`POST /api/tabs` 带 `machine`）；预置可绑定机器（SQLite `presets.machine` 列，空=跟随顶栏当前选择，旧库自动迁移补列）。工作台多机器时顶栏出机器切换 pill（窄屏收进 ☰ 菜单）、网络监控面板按机器分段；**只有一台机器时这些界面元素全部不渲染**。**【裁定 2026-09-05；2026-10-09 补记】切换机器 = 切换该机的 Tab 集合**：顶栏 Tab 条只显示当前选中机器上的 Tab，其它机器的 Tab 仍在后台保活（不关进程、不丢会话），切回去原样可见；当前激活 Tab 若不在新机器上，**优先恢复该机上次激活的 Tab**（本窗口按机器名记忆），没有记忆或已关掉则落到该机最近一个 Tab，再没有则显示空态。绑定了其它机器的预置点开时，顺带把机器选择切到那台，保证新 Tab 立刻出现在条上。设计全文见 [多上游机器支持设计](design/2026-08-24-multi-upstream.md)。新接一台上游机器必须具备：ttyd 以 `-H X-Webauth-User` + `-a` 方式启动并经登录脚本拉起 shell、systemd/LaunchAgent 托管 + keepalive 兜底（照抄 `deploy/ttyd-keepalive.sh` / `deploy/mac/` 模式）、账号登录壳按本机习惯加载提示符与行编辑插件（与下条「还原本机 shell 体验」一致）、且网关到它网络可达；新机器要自己管好防火墙边界（教训：曾只放行单网关出口）。
- **Mac 上游按需唤醒 + 按 Tab 保活（2026-09-06 裁定；2026-09-09 在家抑制）**：Mac 平时照常睡眠；仅当用户主动切换到 Mac、打开 Mac shell 或点击绑定 Mac 的预置时，门禁才可经中继主机家庭网发起一次唤醒并等 ttyd 恢复。**【裁定 2026-09-09】presence 判定「在家」为开时禁止一切 ShellGate 网络唤醒**（Mac 想睡就睡；已在线仍可直连）。在家信号走 presence 服务 `GET /v1/presence` 的 `comfort_home` 字段（示例映射到家庭自动化平台的在家开关），**不用**仅反映局域网在线的信号；presence 查询失败 fail-open（仍允许唤醒，避免 presence 服务挂掉时人在外叫不醒）。配置见 `SHELL_WAKE_HOME_PRESENCE_*`，设计全文 [在家时关闭 Mac 自动唤醒](design/2026-09-09-wake-suppress-when-home.md)。创建 Mac Tab 后，独立租约必须阻止**系统睡眠**（不能只阻止空闲睡眠，否则仍会进 Maintenance Sleep 使网关→Mac 断联）；浏览器切后台、锁屏、网络暂断、被系统暂停或刷新 ShellGate 均不得释放原有 Tab。刷新 / 换浏览器登录按账号恢复服务端记忆的 Tab 与当前选择，禁止暗中新开空终端。用户在 ShellGate 内明确关闭最后一个 Mac Tab 时立即释放；浏览器异常退出没有关闭通知时最多 8 小时自毁。后台健康探测、隐藏 Tab 重连和定时任务不得凭空唤醒；给整个 ttyd 或登录用户安装永久常驻 `caffeinate`、关闭系统睡眠都不合格。实现与排查前必读 [Mac 上游指南](MAC_UPSTREAM_GUIDE.md)。**【裁定 2026-09-10】Mac ttyd 必须走 ShellGate 自建压缩版**（`deploy/mac/build-ttyd.sh` → `shell-gate-ttyd`，ttyd 1.7.7 + lws **4.3.10** + `permessage-deflate`）：Homebrew lws 5.0 默认 `LWS_WITHOUT_EXTENSIONS`，外网全屏 TUI 会一行行刷而中继侧直连正常；**禁止**降刷新/拼帧，也**禁止**给 lws 5.0 开 extensions 上线（粘贴断线，ttyd #1532）。排障全文 [Mac 全屏 TUI 一行行刷](troubleshooting/2026-09-10-mac-corral-line-by-line-refresh.md)。
- Only explicitly configured emails are allowed. Local account/password login is the default and passkeys are optional; external GoTrue is optional.
- 登录成功后签发 HttpOnly Cookie，进入多 Tab 工作台；每个 Tab 独立反代上游 ttyd（注入代认证头 + 可选启动命令）。
- **网页终端必须还原目标机本机 shell 体验（2026-09-05 裁定）**：网页「＋ shell」与预置跑完后的交互壳，须与该机本机终端一致——默认启用账号已配置的提示符、行编辑、指令预测等插件（如上游主机的行编辑增强、Mac 的默认 shell + 提示符主题等），**禁止**再为网页链路单独关掉它们；性能代价接受，不以「网页打字要快」为由裁剪插件。实现要点：`interactiveLoginCommand` 落回 `exec "$SHELL" -li`（不再导出 `SHELLGATE_WEB_TERM`）；空命令（「＋ shell」）仍必须注入 `arg`，否则上游脚本会开 `bash -l`，Mac 进不了默认 shell、上游也丢 `-i`。历史「网页跳过行编辑增强」方案已废止，见 [按键回显排查记录](troubleshooting/2026-08-05-terminal-echo-latency.md) 的裁定补记。
- **会话时效**：Cookie `MaxAge` 与门禁自签会话 JWT 的 `exp` 都由 `SHELL_SESSION_TTL` 控制（默认 `12h`）。登录时只校验一次 GoTrue `access_token`（其自身约 1h 过期），然后换发门禁自己的 12h JWT 写入 Cookie——**不要**把短寿命 `access_token` 直接当会话 Cookie，否则会出现「Cookie 还在但约 1 小时就被踢去重登」。**`SHELL_SESSION_TTL` 非法或 ≤0 必须启动失败**（禁止静默回落默认）；`SHELL_NETMON_INTERVAL` 非法或负值同样 fail-fast（`0` 仍表示只做被动统计）。
- **反代上游是信任边界内的 ttyd（2026-09-05 加固）**：Transport **禁止** `ProxyFromEnvironment`（内网流量与 `X-Webauth-User` 不得进环境代理）；`SHELL_TTYD_*` 地址只允许 `http`/`https`、必须有 Host、**禁止 URL 内嵌用户名密码**。细则见 [门禁放行/配置加固](troubleshooting/2026-09-05-gate-policy-hardening.md)。
- Presets and tabs use local SQLite by default, with optional PostgreSQL for shared storage. Default presets are operator-configured and empty by default. **【裁定 2026-09-07】Tab 目录按账号在服务端持久记忆**（刷新 / 换浏览器登录仍是同一组 Tab；只有工作台内明确关闭才删除；禁止把「本窗口临时状态」当成唯一真相、也禁止有记忆时还暗中新开空 shell）。接回是通用的：再连时注入同一启动命令，**不为任何示例程序写特判**；程序若自带接回则自然生效，普通空 shell 不保证同一屏/同一进程。全文见 [Tab 服务端记忆](design/2026-09-07-tab-server-persistence.md)。**【裁定 2026-09-08；选路 2026-09-09】双活网关 + 共享 Postgres**；按时延选路不走付费 CF LB，改为 apex（`shell.example.com`）登录后竞速跳到 `hk.shell.example.com` / `edge-b.shell.example.com`（`SHELL_COOKIE_DOMAIN` + `SHELL_EDGE_HOSTS`），见 [双入口共享存储](design/2026-09-08-dual-edge-shared-store.md)。**默认项只在该邮箱首次打开预置列表时种一次**（`preset_defaults_applied` 记账）；用户删掉某个默认预置后禁止再按命令名补种——否则管理面板点「删」像没反应（2026-09-05 修）。
- **顶栏就是启动器，不要二级菜单（2026-08-02 定；2026-09-05 压高度）**：`workspace.html` 顶栏平铺「＋ shell」+ 每个预置程序按钮（`#launchers`），点一下直接开 Tab；原来的「新开」弹窗（选启动方式）已删除，不要再加回任何"先点开再选"的中间层。「预置」按钮只负责增删管理。顶栏同时去掉了品牌字样和「退出」按钮（关网页即退出，`/logout` 路由保留）；按钮一律不用渐变填充（用户明确嫌丑），只留描边 + 透明底。**桌面宽屏顶栏必须单行紧凑**：机器 pill + 启动器 | Tab 条（占余量）| 浅色/网络/预置，禁止再拆成「启动一行 + Tab 一行」浪费垂直空间；终端内容优先。Tab 增多只横向滚动，**不得**把顶栏撑高或换行（滚动条抖动同属违规）。窄屏仍收成 ☰ / Tab / ⋯。视觉细则见 [前端视觉重绘](design/frontend-redesign.md)。**禁止把工作台嵌进终端 iframe（2026-09-08）**：`tab.path` 为空时 `src` 会变成 `?rendererType=…` → 解析成 `/?…` → 再画一套顶栏（双层 title bar）。工作台/登录页必须 `frame-ancestors 'none'`，iframe 拉取 `/` 直接 403；`mountTabPane` 只接受 `/t/{id}/`。见 [双层顶栏排查](troubleshooting/2026-09-08-double-title-bar-nested-workspace.md)。
- **快捷命令必须与用户手敲效果完全一致**：注入给 ttyd 的启动命令统一由 `interactiveLoginCommand`（`internal/server/server.go`）包成 `exec "$SHELL" -lic '<命令>'`，命令跑完再 `exec "$SHELL" -li`。**禁止写死 `bash -lic`**：否则 Mac 点预置整段跑在 bash 里，看不到 zsh/提示符主题；Linux 上游 `$SHELL` 本就是 bash，行为与旧写法一致。原因：上游登录脚本用的是 `bash -lc "$*"`，**只读 `/etc/profile` 与 `~/.profile`，不读 `~/.bashrc`**，而 `~/.bashrc` 里的 PATH 追加 / 别名 / 函数 / 工具初始化只对交互式 shell 生效。两者 PATH 顺序不同会解析到同名命令的不同副本——实测曾出现一次性预置命令命中非交互 PATH 下的旧版，终端里敲到的却是交互 PATH 下的新版。加 `-i` 对齐交互环境；ANSI-C 引用 `$'...'` 在 bash/zsh 都可用。修复放在门禁侧而不是上游脚本，是因为上游脚本不在本仓可控范围；上游脚本日后若改成 `-lic`，这里会变成无害的双层 exec，不必同步删。Mac 登录脚本还必须自己补齐 `SHELL`（系统账号壳）与 `COLORTERM=truecolor`——LaunchAgent/ttyd 常不带这两项，缺了会进错壳或把 TUI 主题压成 256 色（与上游 truecolor 声明同口径）。
- **快捷命令跑完必须落回交互 shell，不能让 shell 退出（2026-08-02 修）**：终端页面的唯一进程就是这个 shell，它一退出 ttyd 就关掉 WebSocket，而 `enhance.js` 的断线恢复层会重载页面、反代重写层又重新注入同一条启动命令——于是**会正常结束的一次性命令**陷入「跑完→断开→自动重连→再跑一遍」的死循环，60s/5 次的重连护栏也拦不住（单次运行超过 60s，计数窗口一直被刷新）。常驻型程序（如全屏 TUI）不退出，所以这个坑直到接入一次性命令才暴露。`interactiveLoginCommand` 因此在用户命令末尾追加一行 `exec "$SHELL" -li`；用换行而不是 `;` 拼接，避免命令以注释或后台符号结尾时把收尾语句吞掉。排查同类「Tab 自己反复重启」时，先分清是上游命令退出（本条）还是链路真的断了（重连层），两者症状一样。
- **注入给 ttyd 的 `arg` 里绝不能出现真实换行等控制字符（2026-08-03 血的教训）**：启动命令是当作 URL 查询参数传给 ttyd 的，只要参数里出现 `%0A`，ttyd 依赖的 libwebsockets 直接判握手失败（上游 ttyd 日志 `hs0405 has failed the connection`，网关侧 `反代 ttyd 失败: EOF`，浏览器拿到 502），**所有带命令的 Tab 全部连不上、只有空 shell 能开**，表现是"点了预置程序没反应 / 手机点终端不弹键盘"。所以上一条那个收尾换行必须由 bash 自己展开：用 ANSI-C 引用 `$'…\nexec "$SHELL" -li'`（`ansiCQuote`），URL 里只是反斜杠加 n 两个普通字符。已有单测 `TestInteractiveLoginCommandHasNoRawControlChars` 守这条，**改命令包装后必须真连一次 ttyd 验握手码是 101**（`curl` 带 Upgrade 头打 `http://terminal.example.com:7681/ws?arg=…`），不能只跑单测。
- **按键回显慢的根因几乎总在远端 shell，不在链路上（2026-08-05 实测定论；2026-09-05 产品改口）**：网页终端曾出现回显 P95 500ms+。逐段实测拆解后，**门禁这一侧全是干净的**——ttyd 自身 P50 0.3ms / P95 1.1ms，反代约 2ms，门禁↔终端主机网络 P50 28.5ms / P95 33ms（抖动 0.4ms），浏览器侧无长任务。真正的开销是终端主机上的 `ble.sh`（纯 Bash 实现的行编辑增强层）：**每敲一个字符要消耗约 40ms 的 CPU**，而那台机器只有 4 核、长期负载 7~10，撞上排队后被放大成 300ms 以上。同链路对照：带 ble.sh P50 172ms / P95 280ms，去掉后 P50 29ms / P95 35ms。已排除的替代方案：调优 ble.sh 关掉高亮与自动补全只省 38%；升级到 0.4 nightly 反而更慢。**【裁定 2026-09-05】**曾用 `SHELLGATE_WEB_TERM=1` 让网页会话跳过 ble.sh 换流畅度；用户要求网页端默认还原本机插件（指令预测 / starship 等），**不再跳过**，接受回显变慢。排查「终端卡、打字慢」仍先在终端主机上用不经过网络的方式量远端 shell（`bash -i` 对比 `bash --norc -i`），不要一上来就怀疑网络或反代；**禁止**再把「网页跳过 ble.sh / 强制 bash 丢掉 zsh 插件」当修法加回来。
- **回显时延这个指标本身对全屏 TUI 会失真，改口径前先看它是不是在测幻觉（2026-08-05）**：计时逻辑是「发出按键 → 收到下一帧下行数据」，默认下一帧就是回显。但全屏 TUI 会定时向终端发查询——实测某 TUI 空闲时每 2.00 秒发一帧 `\x1b[?996n` + `\x1b]11;?`；而 TUI 里大量按键根本不触发重绘（实测 30 次按键 23 次无回显），计时器就等到那个 2 秒的查询帧记成「回显」，**120 个样本里 6 次误记就能把 P95 顶到 500ms+，而用户实际打字并不卡**。`enhance.js` 已用 `isTerminalQueryOnlyFrame` 排除纯查询帧，并用 `ECHO_ATTRIBUTION_MS`(600ms) 把等不到回显的样本**丢弃而不是记错值**（错值恰好落在 P95 上，会掩盖真实劣化）。**这段正则必须真跑才测得出对错**（Go 只能断言源码含某字符串），守护测试是 `internal/server/web/enhance_query_frame_test.mjs` + `TestEnhanceQueryFrameFilter`，没装 node 时自动跳过。改动回显计时或新增 TUI 类预置程序时，先读 [按键回显排查记录](troubleshooting/2026-08-05-terminal-echo-latency.md)。
- **终端主机的 CPU 拥堵是所有交互延迟的放大器**：4 核机 `/proc/pressure/cpu` 的 `some avg300` 超过 20% 就在排队，按键路径上的任何计算都会被成倍放大。曾有常驻服务空转吃掉约 1.5 个核（已停，对照回显明显下降），**排查时先看当前 CPU 再翻历史**。某次体感卡时：PSI 排队、全屏 TUI + 多路 agent 进程吃满，同时上游→网关 ping 正常、`Send-Q=0`——是 CPU 不是网络。线上 `perf-sample` 落在网关 `SHELL_DATA_DIR` 下的性能日志（运维自定路径）。详见 [按键回显排查记录](troubleshooting/2026-08-05-terminal-echo-latency.md)。
- **手机端「点终端不弹键盘」的通用修法**：iOS / Android 只在用户手势里真的发生一次聚焦时才弹系统键盘，而 ttyd 在页面加载时就程序化聚焦了隐藏输入框（那次不算手势），之后再点终端焦点没变化、不产生聚焦事件，键盘就可能死活不出来。`enhance.js` 的 `installTapToFocus` 在干净点击（未滑动）的 `touchend` 里把焦点交回隐藏输入框。**【裁定 2026-09-14】**键盘已经打开且输入框仍聚焦时**禁止**再 `blur` 再 `focus`（那会闪键盘并触发整页重绘）；只有父页判定键盘已收（`__shellgate: "keyboard"` 的 `open:false`）才允许在这次手势里再走一次聚焦把键盘唤回。全程不 `preventDefault`，并对同一次 touchend 去重。埋点是 `mobile-tap-focus`（带 `wasFocused`/`nowFocused`/`kept`）。
- **【裁定 2026-09-14】手机终端会话保持软键盘打开**：用 shell 就必须打字；键盘收起再弹起会压高度、重算终端行列，卡而且没必要。触摸优先设备上：① 点过终端、键盘升起之后保持打开——顶栏、Tab、启动器、菜单、快捷键栏、网络小窗标题等非输入控件必须在 `pointerdown` 里 `preventDefault`，不得抢走焦点把键盘收掉；Tab 条空白处要放行，否则横滑切 Tab 会失灵。② 键盘第一次升起后锁住 `--app-height`（只跟更矮、不跟回弹）；转屏/窗口宽度变了才解锁重算。iframe 宽度没变时禁止把 `visualViewport` resize 当成一次 fit。③ 管理预置等真正的输入框除外；关掉后在同一次点击里把焦点交回当前终端。④ 系统键盘收起键、切走 App、锁屏网页拦不住；回来后点终端应唤回键盘，但布局仍用已锁定高度，避免二次重绘。⑤ 仍禁止没有用户手势时 `setTimeout` 抢焦点——本条不是复活「失焦后强行抢焦点」。
- SSH / 运维入口走点对点隧道直连（如 ZeroTier）；**禁止**再依赖已下线的集中运维通道。
- **上游 ttyd 停了不会自愈，排查「终端上游不可用」先看它还活着没**：曾有一次 root 托管的单元（`Restart=on-failure`）收到 SIGTERM 后**以退出码 0 干净退出**，systemd 据此判定是管理员的正常停止操作、**不触发重启**，于是静默停机数小时才被发现，全程网页端显示「终端上游不可用」。判别方法：`systemctl status ttyd-shellgate.service` 看是不是 `inactive (dead)`、`pgrep ttyd` 有没有进程、`ss -ltn | grep 7681` 有没有在监听——**注意从上游本机 `curl` 公网域名本来就可能不通（见网络监控小节），不能拿它当判据**。运维账号没有上游 root 时改不动那份单元，因此另建了一套用户级兜底：`deploy/ttyd-keepalive.sh` + `deploy/ttyd-shellgate-keepalive.service`，装进 `~/.local/bin` 与 `~/.config/systemd/user`（该账号已开 lingering，开机自启、注销不停），`Restart=always` + `StartLimitIntervalSec=0`。包装脚本启动前会先看 7681 是否已被占用，占着就原地等待，**不与 root 那份单元抢端口**，两套监管可共存。已实测「干净 SIGTERM → 约 3 秒自动拉起」。**根治仍需 root 把那份单元改成 `Restart=always`**，改完这套兜底降级为双保险，不要因此删掉它。
  - 另一个已知的误判点：`ttyd` 起来后 `/proc/<pid>/cmdline` 会显示成 `-t rendererType canvas`（两段），看着像参数写错了，其实是 ttyd 1.7.7 用 `strsep` 就地改写 argv 造成的假象；真写错会直接 `invalid client option` 退出、根本起不来，所以「进程还在监听」本身就是参数正确的证据。
- **终端增强脚本注入**：`newTTYDProxy` 的 `ModifyResponse`（`internal/server/server.go`）会给 ttyd 返回的 `text/html` 响应注入 `<script src="/__shellgate/enhance.js">`（正确处理 gzip 与 Content-Length），让浏览器侧脚本（`internal/server/web/enhance.js`）拿到 ttyd 暴露的 `window.term` 做：修复中文全角标点丢失、截图当前终端画面压缩进浏览器剪贴板、把剪贴板图片压缩后经括号粘贴通道送进内嵌的 agent、OSC 52 / 手动选区复制桥接，以及**手机端键盘避让 + 触摸滚动 + 快捷键栏**（`/` `@` Esc Tab 粘贴 `^C` Ctrl 方向键）。**图片粘贴的哨兵协议**（`CORRAL_IMG_BEGIN` / `CORRAL_IMG_END`）是与上游 TUI 程序之间的跨仓库约定：门禁侧只发出新哨兵对，对端解析需兼容旧哨兵对（过渡期已打开的网页终端）。改动任一侧都要同步另一侧，否则图片粘贴静默失效（对端会把整段哨兵文本当普通文本发给 agent）。
- **手机端布局（2026-07-22 重写；2026-09-14 锁高度）**：工作台 `workspace.html` 是键盘可视区的唯一负责人，用 `visualViewport` + `interactive-widget=resizes-content` 把整页（含 iframe）压到当前可见高度，并在键盘第一次升起后锁住该高度（见上条 2026-09-14 裁定）。iframe 内禁止再次推算键盘高度、映射父页可视区、延迟猜测键盘状态或用焦点状态锁定工具栏位置；父页可以把「键盘开/关」经 `postMessage` 告诉 iframe，只用于决定点终端时要不要 `blur`。`enhance.js` 把终端容器与两行快捷键栏作为同一纵向 flex 布局的两个同级区域，工具栏真实占据底部空间、不覆盖终端。尺寸变化通过 `ResizeObserver`/单帧调度触发 fit——**键盘开合不得再改行列**，转屏才重算。快捷键使用 `button`（`tabIndex=-1`），`pointerdown` 仅阻止浏览器转移焦点，`pointerup` 才发送一次按键；禁止恢复旧的 `label for=textarea`、`touchstart` 直接发送、MutationObserver 持续改写隐藏输入框位置、失焦后强行抢焦点等机制。单指滑动仍转成本地滚动或 SGR 滚轮（canvas 渲染器本身不处理触摸滚动）。
- **终端贴边（tightFit）的两条铁律（2026-08-02 修「右侧黑边」）**：`enhance.js` 的 `tightFitTerminal` 负责把字符网格铺满容器（骗 FitAddon 滚动条宽=0 → 补列/行 → 半格余量做 scale）。踩过的两个坑：
  1. **冪等指纹不能只看容器像素盒**。旧实现拿 `#terminal-container` 的宽高当指纹，首屏那一次贴合就成了最后一次——后面 300ms / 1000ms 的重试全被跳过。而 ttyd 是**在 WebSocket 握手拿到服务端下发的选项后**才套用字号/字体/渲染器的，那一刻容器尺寸一动不动、字符网格却整体重算，于是右侧留下一条黑边，直到用户手动改窗口大小（容器变了才放行重算）才消失。现在指纹改为容器像素盒 + `cols/rows` + `.xterm-screen` 的 `offsetWidth/offsetHeight`（`tightFitStateKey`），并补了 `document.fonts.ready`、`term.onResize`、2.5s 兜底重试三个触发点。指纹按「贴合完成后」的状态记录，量不到网格时不写，留给后续重试。
  2. **量尺寸前必须先清掉上一轮的 `transform`**。`getBoundingClientRect` 返回的是**含 transform 的视觉尺寸**，带着旧 scale 去量会得出「已经没有空隙」的假象，进而清空 transform、黑边又回来——两次事件之间来回翻烧饼。判定 `offsetWidth` 才是不受 transform 影响的布局尺寸，指纹用它、测量前清 transform，两件事要一起做。
  改这块仍要守住原来的冪等初衷：无条件 `term.fit()` 会让隐藏 textarea 一瞬失焦，手机软键盘反复开合。新增触发点必须是一次性的或经指纹过滤，`term.onResize` 回调还要有重入保护（`term.resize()` 会同步派发它）。
- **默认渲染器是 canvas；截图仍保留 WebGL 的 `preserveDrawingBuffer` 补丁（2026-08-05 测、2026-08-31 改默认）**：ble.sh 修完后浏览器纯绘制段 canvas P50 70.7ms / P95 101.8ms，WebGL 是 26.5 / 43.6ms。那次为了 44ms 把 iframe 改成 `?rendererType=webgl`。**2026-08-31 裁定改回 `?rendererType=canvas`**——Corral 流式中文会把 WebGL 图集挤爆，中文消失/花屏，自愈盖不住（见下条）。URL 查询参数仍优先于 ttyd 启动 `-t`。canvas 下截图走 2D 画布，本来就能 `drawImage`；`enhance.js` 的 `getContext` 猴补丁继续对 `webgl`/`webgl2` 强制 `preserveDrawingBuffer: true`，因为有人强制 webgl、或 WebGL 上下文丢失后 ttyd 可能再拉起它，裸 WebGL 截图是全黑的。对照实验：开此开关与裸 WebGL 渲染延迟无差别（26.5 vs 27.0ms）。**改用 WebGL 引入过的「渲染器回落」仍要守**：上下文丢失时 ttyd 会 `webglAddon.dispose()` 回落到 DOM——终端能用、页面上一个 canvas 都没有，`captureTerminalCanvas` 必须提示「刷新页面即可恢复截图」，不能只在控制台报错。Safari / iOS 并发上下文上限更严。xterm `WebglAddon` 构造函数本身收 `preserveDrawingBuffer`，ttyd 没暴露；上游暴露了就可以去掉猴补丁。
- **TUI 中文乱码：禁止让用户按快捷键修，默认用 canvas 避开 WebGL 图集（2026-08-31 裁定）**：Corral 用着用着中文消失或变成怪字，不是链路、也不是远端把缓冲区写乱了。根因是 ttyd 1.7.7 捆的 xterm 5.4.0 WebGL 纹理图集：CJK 宽字符（占 2 格）在图集 LRU 驱逐时左右半格不能原子清空。同类指纹见 WaveTerm [#3386](https://github.com/wavetermdev/waveterm/issues/3386)（复制出来的字是对的、关掉 WebGL 即不再现）；[#6038](https://github.com/xtermjs/xterm.js/issues/6038) 的页合并/溢出是同一类图集病，补丁在 `@xterm/xterm` **6.1.0-beta.289**（不是 7.0.0）。**产品约束：使用中画面必须保持正确，禁止把 Ctrl/Cmd+Shift+K /「修复显示」当主路径。** 2026-08-17/20 的 `clearTextureAtlas` 自愈失败：Corral 流式刷中文是局部行更新，`isFullViewportRedraw`（半屏以上）经常判不中，8s 懒修也等太久，而且自愈是事后补洞——用户已经看见乱码了。门禁换不了 ttyd 内置 xterm（webpack 打进二进制；addon-webgl 0.20 对不上 5.4.0 API；ttyd master 仍是 xterm 5.5.0 / webgl 0.18.0，升 ttyd 也没有那批补丁）。**所以默认 `?rendererType=canvas`**（ttyd 已有 CanvasAddon）。代价是绘制段回到 canvas 的 P50 70ms；相对「中文用着用着就坏」，接受这 44ms。canvas 选区必须继续用 8 位 alpha 的 `selectionBackground`（#2737）。贴图自愈代码留作 WebGL 被重新打开时的双保险，不要删，但不要再靠加触发点消乱码。守卫测试 `TestRootServesWorkspaceWithCanvasRendererQuery` + `TestEnhanceJSSelfRepairsDisplayCorruption`。排查、改渲染器或想把 WebGL 加回来时先读 [TUI 乱码与显示自愈](troubleshooting/2026-08-20-tui-display-corruption.md)。**禁止为了那 44ms 把默认改回 webgl**，除非上游 ttyd 捆到带宽字符图集修复的 xterm（≥6.1.0-beta.289 且用 CJK 洪泛验证过不再花屏）。
- **深浅色主题：跟随系统 + 手动锁定（2026-08-05 上线）**：三档偏好 `auto`/`light`/`dark` 存浏览器 `localStorage`（键 `shellgate_theme_pref`，每台设备各自独立，服务端不存）。**父页 `workspace.html` 是配色唯一真相源**：它用 `matchMedia("(prefers-color-scheme: …)")` 解出生效档位，一边打在 `<html data-theme>` 上驱动外壳的 CSS 变量，一边把 xterm 主题对象 `postMessage` 广播给所有终端 iframe。iframe 内部**只负责接收，不得自行推算深浅色**（不要在 `enhance.js` 里再读一次媒体查询——两套判断迟早不一致）。要点：
  - **深色主题对象刻意只带 `selectionBackground` 一个键**（`TERM_THEME_DARK`）。xterm 对未指定的键回落到默认色，所以从浅色切回深色能完整还原改动前的观感，不必维护一份深色全量色表；反过来说，**不要给它补全 16 色**，那等于偷偷改了深色下的既有观感。
  - **切换走运行时换肤，绝不能重开终端**：`enhance.js` 收到广播后直接改 `term.options.theme`（xterm 5.4.0 支持），颜色立即重绘。**不要退回「重载 iframe」那种实现**——那会换掉 shell 进程、打断正在跑的命令。已实测：连切三次主题后 shell 的 `$$` 与 `jobs` 均不变、重连计数 0。首帧配色由父页拼 iframe 地址时带上的 `theme=` 查询参数负责，避免先按深色画一帧再变白的闪烁。
  - **贴边留白的底色必须跟着主题走（黑边回归点）**：`installTerminalBleedStyles` / `installMobileStyles` 里那 6 处底色是 `var(--sg-term-bg,#000)`，由主题广播写入。**改回写死的 `#000` 会让浅色下右侧/底部露出黑边**——这正是 tightFit 半格余量所在的位置。手机快捷键栏、截图按钮、剪贴板提示条、粘贴兜底框同理走 `--sg-*` 变量。
  - **选区色两套都必须带 8 位十六进制 alpha**（深 `#5DA5D559` / 浅 `#0550AE29`）。这是 canvas 渲染器时代踩过的坑（选区独立图层不透明就盖字）；WebGL 本身不踩，但上游回落 canvas 时仍要守住。单测 `TestRootServesWorkspaceWithBothTerminalColorSchemes` 会遍历页面里**每一处** `selectionBackground` 字面量强制这条，并守住两套配色都还在。
  - **跨仓库约定：上游 TUI 及其内嵌 agent 自动跟随，门禁侧不需要为它做任何额外通知。** 上游 TUI 启动时查一次、运行中定期复查终端背景色（OSC 11），并把结果转发给它托管的 agent 会话。**门禁这边唯一要保证的就是「终端如实回答背景色查询」**——已实测运行时换肤后答案会跟着变（深浅色回答与设定一致），对端来回切换均在 2 秒内跟上。ttyd 1.7.7 内置的 xterm.js 5.4.0 **早于** DEC 2031「配色变了主动通知程序」那套协议，做不了推送，靠对端轮询即可，不值得为此升级上游 ttyd。
  - **已知代价（不是 bug，别去修）**：已经在跑的非 TUI 程序（vim、bat、带色日志）只在启动那一刻问一次底色，切换后不会回溯变色，重启该命令即可。
  - 登录页 `login.html` 本次未纳入，仍是固定深色。
- **断线自动恢复（2026-07-27 上线）**：ttyd 1.7.7 的重连坑在两点——**正常关闭（WS code 1000）只显示 "Press ⏎ to Reconnect" 等用户手点，不自动重连**；异常关闭也只在断开当下立刻试一次。手机锁屏/切后台回来常卡在「要手点」或「那次自动重连趁没联网就失败了然后放弃」。**保活这层其实已由 ttyd 服务端每 5s 的 libwebsockets ping 覆盖**（前台链路空闲不会被中间网关掐），真正缺的是恢复层。修复：`workspace.html` 给 iframe `src` 加 `disableReconnect=true` 关掉 ttyd 自带重连（避免两套打架），恢复统一交给 `enhance.js` 的 `installConnectionKeeper`——它复用已有的 `window.WebSocket` 包装层（`installWebSocketProbe` 里维护的 `liveConn`）监听 `/ws` 关闭，连接一断且**页面在前台+已联网**就自动重连；重连方式是 `location.reload()` 重载 ttyd 页面（反代响应改写与请求重写层会重新注入启动命令，自带接回的程序自动接回原会话，用户基本无感）。`visibilitychange`/`online`/`pageshow` 回前台或网络恢复时立即触发。**用 `sessionStorage` 做 60s 内最多 5 次的重连护栏**：命令秒退或上游长时间不可用（含 shell-gate 重启后内存态 Tab 丢失导致 `/t/{id}` 404）时会无限刷屏，超限即停手、写一行提示等用户点击/按键手动重连。改这块要留意：`disableReconnect` 与 `installConnectionKeeper` 是一对，去掉任一侧要么退回「要手点」、要么两套重连打架。
- **手机端触摸滚动灵敏度**：`enhance.js` 的 `installTouchScroll` 里手指位移到滚动量的放大系数（`applyScroll(delta * N)`）是唯一的灵敏度旋钮，2026-07-27 从 `2.5` 降到 `1.25`、2026-08-02 再降到 `1`（1:1 跟手，用户两次反馈过灵敏）。
- **快捷键栏形制（2026-08-02 定）**：固定两行、**每行 6 键**，行1 `/ @ Esc Tab 粘贴 ^C`，行2 `Ctrl Alt ↑ ↓ ← →`；Alt 与 Ctrl 一样是粘滞键，可叠加（Alt 走 ESC 前缀，即 Meta-sends-Escape）。增删按键要保持每行 6 个，并同步 `MOBILE_TOOLBAR_MIN_HEIGHT`（= 两行 36px + 行间距 4 + 上下内边距 12 = 88）。工具栏内边距上下都是 6px、**不再叠加 `env(safe-area-inset-bottom)`**——父页已用 `visualViewport` 把可视区压到不含系统条的高度，再补安全区就是多出一截底部空白（用户实测反馈）。
- **Mac 客户端把 Command 当 Ctrl 用（2026-08-03 上线）**：终端协议只认 Ctrl / Alt(Meta) / Shift，**Command 没有任何字节表示**，按下去服务端永远收不到——所以只能在浏览器侧翻译。`enhance.js` 的 `installCommandAsCtrl` 只在苹果客户端（`isAppleClient`）装，把 `Command+字母` 转成对应控制字符送进 PTY（Cmd+D → 0x04，与物理 Ctrl+D 完全等价），另含 `[ ] \ - /`。三条边界，改之前先看清：
  1. **C / V 必须放行**：Command+C / Command+V 是本页复制粘贴的唯一入口（接的是浏览器 `copy`/`paste` 事件，见下面剪贴板小节），抢过来当控制字符，剪贴板与图片粘贴哨兵整个失效；而 Command+C 在无选区时本来就会被转成真正的 Ctrl+C，中断命令的效果早就有了。
  2. **Cmd+W / T / N / Q 拦不住**：Chrome / Safari / Edge 把标签页、窗口级快捷键留给自己，页面收不到事件、`preventDefault` 也无效；Safari 另外独占 Cmd+R / Cmd+L。所以删词只能按物理 Ctrl+W，别指望 Command 版本（会直接关掉页面）。
  3. 带 Ctrl / Alt / Shift 的组合一律放行（Shift 是为了不抢 Cmd+Shift+V 一类粘贴变体）。
  拦截写在 `document` 的**捕获阶段**：捕获期 `stopPropagation` 后事件到不了 xterm 的隐藏输入框，因此不必动 `attachCustomKeyEventHandler`，也不会和几个剪贴板监听打架。代价是终端页里 Cmd+A/F/R/L/D/S/P 的浏览器功能让给了终端（刷新走浏览器菜单或 F5）。**单测只能守住代码形状，改动必须用真实浏览器验**：headless Playwright 伪装 Mac UA 直连 `/t/{id}`，敲字后按 Meta+U 看整行是否被清（等价 Ctrl+U），并确认 `cmd-as-ctrl` 埋点里没有 `c`/`v`。
- **顶栏窄屏收纳（2026-08-03 上线）**：`workspace.html` 在 `max-width: 760px` 下把平铺的启动器与「网络 / 预置」整体隐藏，改成左右两个入口——左 `☰` 是启动菜单（＋shell + 全部预置，与顶栏平铺的是同一份数据、同一套 `renderLaunchers`），右 `⋯` 是「网络监控 / 管理预置」。中间只留 Tab 条。**这不违反「顶栏就是启动器、不要二级菜单」那条**：宽屏仍然一点即开，收纳只在放不下时发生，且菜单里仍是一层直达、没有「先选启动方式」的中间层。

- **网络监控（2026-08-03 上线）**：顶栏「网络」进入，面板在 `workspace.html`，服务端在 `internal/server/netmon.go`。整条链路拆三段，**每段只能由唯一量得到的一方去量**，不要试图在别处推算：
  - **展示形态必须是右上角无阻塞悬浮小窗，不是模态弹窗（2026-08-03 用户纠正）**：不加全屏遮罩，打开时终端仍可点击、输入和接收回显；小窗限制为窄宽和 28rem 高度上限，正文自行滚动，同时支持收起、关闭和顶栏按钮开关。标题栏与按钮按下时不得抢走终端焦点，否则手机软键盘会收起；收起后关闭再打开必须恢复展开状态和一致的图标。改完必须用真实浏览器分别验桌面与手机尺寸，并在小窗打开时实际向终端输入，不能只看静态样式。
  - 下行段（浏览器 ↔ 门禁）：只有浏览器测得到，打 `/api/netmon/ping` 取往返。
  - 上行段（门禁 ↔ 终端主机）：只有门禁测得到，`httptrace` 拆出 TCP 建连与首字节两段（前者纯网络，后者含上游处理，分开才知道慢在哪边），外加每次真实开终端的握手耗时（免费样本，不额外发包）。
  - 端到端（按键 → 回显）：只有终端 iframe 里测得到，`enhance.js` 在 ttyd 的 WebSocket 上做单时钟往返，经 `postMessage` 递给父页汇总。
  - **一律用「同一个时钟上取两次时间」算往返，不要用发送方时间戳**：两端系统时钟不同步，单向时延不可信；WebSocket 又没有请求-响应语义，浏览器 API 也不暴露原生 ping/pong，往返只能自己构造。
  - **代理字节必须在 `net.Conn` 这层统计**：ttyd 走 WebSocket，反代在 101 之后就退化成裸字节对拷，`ModifyResponse` 之类的响应钩子**完全看不到终端流量**。所以 `newTTYDProxy` 自带 `Transport`，拨号口既做握手采样又把连接包成 `countingConn`。这个包装层有两条硬性约束：**不能实现 `ReadFrom`/`WriteTo`**（那两条快路径会绕开 `Read`/`Write` 直接搬字节，统计就漏了），**必须转发 `CloseWrite`**（反代靠它做 TCP 半关闭，吞掉上游收不到 EOF）。自带 Transport 还必须 `ForceAttemptHTTP2: false`——WebSocket 升级只能走 HTTP/1.1。**动过 Transport 就必须真连一次验 101 握手**，单测覆盖不到升级路径。
  - **上游探测必须带 `X-Webauth-User`**：ttyd 用 `-H X-Webauth-User` 鉴权，不带身份只回 407，量到的是「被拒绝」的耗时、走不到真实处理路径。身份取白名单里字典序最小的邮箱（`Config.probeIdentity`，保证重启后口径一致）。探首页不会 fork shell，只有 `/ws` 才会。
  - **ttyd 的客户端命令是二进制，不是字符串（血的教训）**：协议是「1 字节命令码 + 载荷」（`'0'` 输入、`'1'` 改窗口大小、`'2'/'3'` 暂停恢复），但 ttyd 1.7.x 用 `TextEncoder` 编码成 `Uint8Array` 再发。第一版回显计时只判 `typeof data === "string"`，结果**一条输入帧都认不出来、样本恒为 0**，代码看着完全正常。识别统一走 `ttydInputFrameSize()`，字符串与二进制两种形态都认，已有单测守着。
  - **回显计时的「安静门槛」不能定高**：屏幕连续刷屏时收到的下一帧未必是这次按键的回显（会把时延测偏低），所以要求终端安静一小段才起表。但门槛定成 200ms 时，正常打字速度下几乎每一击都被跳过（实测 20 次按键只落 1 个样本）；降到 80ms 后 20/20 全中，同时仍挡得住刷屏。
  - 浏览器每 20s 把自己那两段推到 `/api/netmon/sample` 归档，快照里一并返回；`netmon-sample` 与 `perf-sample` 一样落 `perf-log.ndjson`，不污染功能埋点。
  - 探测间隔由 `SHELL_NETMON_INTERVAL` 控制（默认 `15s`，设 `0` 只做被动统计不发探测包）。
  - **本机经公网域名连自己的上游可能不通**：发夹 NAT 下 TCP 直接超时（不是拒绝），网关侧访问一切正常。本机要端到端验证就在 `127.0.0.1` 另起一个 ttyd 实例指过去，别把这个当故障排查。顺带一个坑：手敲启动 ttyd 时 `-t rendererType=canvas` 必须写成一个参数，写成 `-t rendererType canvas` 会直接报 `invalid client option` 退出（systemd 里那份能跑是因为传参方式不同）。
- **剪贴板"往外复制"其实是两条完全独立的路径，不要混为一谈**：(1) agent/上游 TUI 主动发起的复制走 OSC 52（`installClipboardBridge`，2026-07-20 上线，因为浏览器对无用户手势的 `navigator.clipboard.writeText()` 有安全限制，改成缓存+点击同步）；(2) 用户自己拖选画面上任意文字（含内嵌 agent 的聊天内容）后按复制键，走 `installManualSelectionCopy`——这条路径完全不经过 OSC 52。第一版只做了 (1)，用户反馈"选中 agent 聊天内容复制不出来"时才发现这其实是 (2) 的需求，两者症状类似但根因和修复完全不同，以后类似"复制不出来"的反馈要先分清用户到底是要哪一条。
  - **(2) 的真实根因（诊断日志实测证据，不是推测）**：`term.getSelection()`（xterm 自己的选区**内容**模型）在全屏 TUI 场景下**始终是空的**——上游 TUI 自己接管了鼠标、自己在内部维护选区状态判断复制/中断语义。真正生效的是：物理 Ctrl+C 被 xterm 正常编码发到远端，上游 TUI 自己判断有没有选区，有则触发 OSC 52（汇入路径 (1)）。**Mac 用户的 Command+C 到不了这条链路**——它是 Mac 上“复制”的系统保留组合键，浏览器/xterm 不会把它编码成终端里的 Ctrl+C 控制字符。2026-07-22 的第一版曾监听 Command+C 的 `keydown` 再模拟 Ctrl+C，但真机日志证明 macOS 浏览器会直接走标准 `copy` 事件、这条监听根本收不到。当前修复：统一监听浏览器 `copy` 事件；xterm 有原生选区时同步写 `ClipboardEvent.clipboardData`，没有时用 `sendToPty("\x03")` 把复制动作交给上游 TUI 判断。Command+V 同理由标准 `paste` 事件兜底，文本显式走 `term.paste()`，图片仍优先走既有压缩哨兵协议；不要再依赖隐藏输入框的默认复制粘贴行为。
    - **勘误（2026-07-20 补）**：上面这条曾经写过"画面上的拖选高亮是上游 TUI 画出来的，不是浏览器原生选区"——这句话不准确，且直接导致了下面这条 bug 排查走了弯路。`term.getSelection()` 拿不到内容只说明 xterm **选区内容模型**是空的；但拖拽时那块可见的高亮矩形，是 xterm.js 自己的**选区渲染层**画的，跟内容模型是否为空无关——这是两件独立的事，不能因为内容模型是空的就推断可见的高亮效果也是别处（上游 TUI）画的。
  - **截图按钮的剪贴板兼容性**：`navigator.clipboard.write()` 部分浏览器（尤其 Safari）只认 `image/png`，不认 `image/jpeg`；改成同一个 `ClipboardItem` 里带 `image/jpeg`（体积可控，压到 500KB 上限）+ `image/png`（全兼容兜底，不限体积）两种表示，目标 App 自己挑支持的格式。
  - 排查这类"点了没反应"的问题时，**先看 `SHELL_DATA_DIR/debug-log.ndjson` 里的真实埋点再动手**，不要凭猜测改代码——本轮好几次修复方向都是靠这份日志纠偏的。
  - **卡顿 / 流畅度诊断（诊断版可观测性）**：浏览器侧 `enhance.js` 每 5s 上报 `perf-sample`（渲染次数、WS 上下行、longtask）到网关 `SHELL_DATA_DIR` 下的性能日志（与功能埋点分开，超 5MiB 轮转）。隐藏 Tab / 无活动不上报。卡顿当下在 **上游主机** 再采链路：`deploy/sample-ttyd-lag.sh`（或下方命令）。判读：
    - 高 `renderCount` + 高 `longTaskMs`，且 `ss Send-Q`≈0 → 偏浏览器主线程/渲染 → profile the browser render path; do not lower refresh rate (2026-09-10 ruling)
    - `Send-Q`/`notsent` 升高，或会话 `wchar` 逼近 ~100KB/s 而上行 RTT 尚可 → 偏上游→网关上行排队 → verify transport compression and delivery backlog; do not merge output frames (2026-09-10 ruling)
    - 两者都低但仍「慢半拍」→ 偏 RTT → **限流帮不上**

    ```bash
    # 上游主机本机快捷采样（只读）
    bash deploy/sample-ttyd-lag.sh
    # 或手动：
    ss -tnpi | grep -A1 ':7681'
    ping -c 5 <上游主机>
    ```
  - **图片粘贴桥接（`installImagePasteBridge`）曾被截图功能的双格式改动反向坑了一次**：`e.clipboardData.items` 里同一份截图会同时出现 `image/jpeg` + `image/png` 两个候选，2026-07-20 真机日志实测（`paste-image-detected` 埋点，6 次连续复现）确认 Chrome 对其中 `image/jpeg` 这个候选调用 `getAsFile()` **稳定返回 null**（`image/png` 正常），而当时代码只取"第一个 image/* 类型"就不再往下试，命中 jpeg 时直接判定粘贴失败（不是随机偶发，是必现）。修复：遍历所有 `image/*` 候选，依次尝试 `getAsFile()`，拿到第一个非空 File 就用——不要只取第一个类型就假设它能用。这类"多格式候选里挑一个能用的"场景以后要留意同样的坑。
  - **拖选文字时选区整块盖住底下的字（"蒙了一层"）——排查经过两次误判，最终根因在上游 TUI 的选区渲染，不在 xterm.js（2026-07-20 排查记录，含勘误）**：
    - **误判一**：先当成上游 TUI 选区列坐标算错，改了偏移量算法（按 cell 宽度而不是字符数推进）。这修的是**另一个真实但无关**的 bug（CJK 宽字符导致拖选定位缓慢跑偏），修复本身正确、保留，但不是"整块盖住看不见字"的根因。
    - **误判二**：又当成 canvas 渲染器切换引入的 xterm.js 已知问题（官方 issue [#2737](https://github.com/xtermjs/xterm.js/issues/2737)/[#2808](https://github.com/xtermjs/xterm.js/issues/2808)：canvas 把选区画在文字层上面的独立图层，`selectionBackground` 不透明就盖住文字），在 `workspace.html` 给 iframe 追加了 `&theme={"selectionBackground":"#5DA5D559"}`（8 位十六进制末两位是 alpha 通道）。用户实测"还是不行"。
    - **真正的根因（headless 启动真实 app 打印证据确认，不是推测）**：全屏 TUI 申请了鼠标捕获，**拖选事件被 xterm 转发给上游 TUI 自己处理，xterm 从不做原生选区**（诊断日志里 `ctrlc-keydown` 的 `selLen` 一直是 0 早就是这个信号，只是当时没据此下判断）。可见的高亮是 **上游 TUI 的自绘选区**画的。其默认透明前景在自定义行渲染里被**预解析成与选区背景相同的具体色**，整段套上去后前景==背景，文字隐形。修复在上游 TUI 侧：透明前景时只取背景、保留每个文本段原前景色。
    - **两个教训**：① `term.getSelection()` 内容模型为空（`selLen:0`）本身就说明 xterm 没在做选区、拖选被 app 抢走了，可见高亮是 app 画的——这是判断"选区在哪一层"的决定性信号，别再假设"看得见的高亮=xterm/ttyd 画的"。② 排查渲染类问题要 headless 启动真实 app 打印解析后的样式值拿实锤，不要靠肉眼颜色猜。
    - **`workspace.html` 的 `selectionBackground` 透明化保留、但不是为这个 bug**：它对的是**原生 xterm 选区**的场景——工作台里非全屏 TUI 的普通 shell / 其它预置程序不申请鼠标捕获，用户拖选走的是 xterm 自己的 canvas 选区，此时那个 xterm 已知问题是真的，半透明 `selectionBackground` 是这些 tab 的正确默认值。它对自绘选区的 TUI 不生效（也不该由它负责）。


## Browser zoom

Browser page zoom must keep embedded terminals fitted to the available workspace and mouse selection/reporting aligned with the displayed cells. Refit after layout or device-pixel-ratio changes without reloading terminal sessions. Preserve mobile keyboard height ownership and idempotent fitting.
