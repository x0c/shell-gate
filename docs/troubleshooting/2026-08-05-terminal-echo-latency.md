# 按键回显慢 / 回显 P95 虚高：分段定位法与两个真实根因

2026-08-05 排查「网页终端按键回显 P95 500ms+」的完整记录。结论分三层，**不要混为一谈**：

1. **普通 shell 标签页会因 ble.sh 变慢**——根因是终端主机的行编辑插件（P95 可达 280ms）。曾用跳过 ble.sh 降到 35ms；**【裁定 2026-09-05】网页端默认保留插件**，接受回显变慢（见下文「曾采用的修法」）。
2. **Corral 标签页的数字是测量口径错**——回显计时器把 TUI 的定时查询帧误记成按键回显，已修复口径。
3. **浏览器 canvas 渲染曾是 ble.sh 之外的杠杆**——一度改 WebGL 换绘制段延迟；后因 TUI 中文花屏改回 canvas（见乱码排查记录）。

## 一、先照这个顺序分段，别一上来怀疑网络

每一段都要用**不经过下一段**的方式单独量。实测下来，门禁与网络这几段全都是无辜的，
所以**默认先怀疑远端 shell / 远端程序**，最后才怀疑链路：

| 段 | 怎么量 | 2026-08-05 实测 |
|---|---|---|
| 内核 tty 回显 | pty 里跑 `cat`，写一个字节计时 | P50 0.06ms |
| 远端 shell 处理 | 同上但跑 `bash -i`，再对比 `bash --norc -i` | **P50 64ms vs 0.1ms** |
| ttyd 自身 | ttyd 直接跑 `cat`，本机连 | P50 0.3ms / P95 1.1ms |
| 门禁↔上游主机网络 | 从网关连上游主机的 ttyd | P50 28.5ms / P95 33ms，抖动 0.4ms |
| 门禁转发 | 经门禁 vs 直连 ttyd 的差值 | 约 2ms |
| 浏览器↔门禁 | 复用连接后的单次往返（见下方"代理路径"） | 客户端宽带约 35ms |

**`cat` 与 `bash` 的对比是整套方法的关键一步**：`cat` 的回显完全由内核行规程完成，
不涉及任何用户态处理。`cat` 快而 `bash` 慢，就锁定问题在 shell 配置，与链路无关。

### 别被这几个假象带偏

- **CPU 排队不是 shell 慢的原因，是放大器。** 一度怀疑是调度延迟，用管道乒乓
  （两进程互相唤醒，不碰 pty / 终端 / 网络）实测 P50 0.05ms、P95 0.2ms——**进程唤醒毫无问题**，
  假设被证伪。真正的机制是 shell 本身需要大量 CPU，撞上排队才被放大。
- **负载波动会让墙钟时间的 A/B 完全失效。** 逐项开关 ble.sh 选项时，几轮结果在
  P50 32~69ms 之间乱跳，噪声大于效应。改测**每次按键消耗的 CPU 时间**（读
  `/proc/<pid>/stat` 的 utime+stime+子进程时间，除以按键次数）后立刻分出高下——
  这个指标不受负载影响，是横向比较 shell 配置开销的正确口径。
- **`bash -lic '...'` 里读不到 `BLE_VERSION`，不代表 ble.sh 没配置。** ble.sh 不会
  attach 到 `-c` 形式的调用。验证加载状态必须开真实交互式会话（pty + `bash -li`）再敲命令，
  否则会误判成"本机会话也丢了高亮"。

### 代理路径只影响建连，不影响打字

终端域名在部分网络解析到路由器的分流地址。实测：**建连**（含 TLS 握手）比直连公网 IP
慢约 85ms，但**连接建好后的单次往返只差 2~3ms**（35ms vs 33ms）。所以它影响开新标签页和
断线重连的体感，与按键延迟无关，不要在这上面花时间。

## 二、根因一：ble.sh，每敲一个字符约 40ms CPU

终端主机 `~/.bashrc` 里加载了 `ble.sh`（纯 Bash 实现的行编辑增强层，提供语法高亮与历史建议）。
实测每次按键消耗约 40ms **纯 CPU**；机器只有 4 核且长期负载 7~10
（`/proc/pressure/cpu` 的 `some avg300` 约 50%），撞上排队后放大成 300ms 以上。

同链路对照（同一时刻、同样负载）：

| 配置 | P50 | P95 |
|---|---|---|
| 带 ble.sh | 172ms | 280ms |
| 去掉 ble.sh | 29ms | 35ms |

29ms 正好等于纯网络往返，**其余环节全部归零**。

**已排除的替代方案**（别再重试）：关掉语法高亮与自动补全只省 38%，仍有明显延迟；
升级到 0.4 nightly 反而更慢（每次按键 82ms vs 0.3 的 72ms）。

**曾采用的修法（已废止）**：门禁曾导出 `SHELLGATE_WEB_TERM=1`，终端主机 `~/.bashrc`
见到它就跳过 ble.sh。**【裁定 2026-09-05】**用户要求网页端默认还原本机插件（指令预测 /
starship 等），不再跳过；门禁改为落回 `exec "$SHELL" -li`，接受回显变慢。
**禁止**再把「网页跳过 ble.sh」当默认修法加回来。诊断路径仍有效：先量远端 shell，
再怀疑网络/反代。

## 三、根因二：全屏 TUI 标签页的回显数字是口径错，不是真卡

**现象**：普通 shell 已经降到 29ms 之后，全屏 TUI 标签页的面板仍显示 P95 500ms+。

**根因**：回显计时器的算法是「发出按键 → 收到下一帧下行数据」算差值，默认下一帧就是回显。
但全屏 TUI 会定时向终端发查询——实测空闲时**每 2.00 秒**发一帧 48 字节的
`\x1b[?996n` + `\x1b]11;?`（问配色方案与背景色，即跨仓库主题约定）。
而 TUI 里**大量按键根本不产生重绘**（方向键、Esc、焦点不在输入框、程序正忙时的按键——
本机实测 30 次按键有 23 次完全没有回显），计时器就一路等到那个 2 秒的查询帧并记成一次
「回显」，样本值可达 2000ms。**120 个样本里只要有 6 次这种误记，P95 就被顶到 500ms+。**

**修法**（`enhance.js`）：

- `isTerminalQueryOnlyFrame`：整帧去掉终端查询序列后不剩内容的，不用来停表，也不刷新"安静"基准。
- `ECHO_ATTRIBUTION_MS`（600ms）：超过这个时间还没等到回显，判定这次按键压根没有回显，
  **样本丢弃而不是记一个错值**——错值恰好落在 P95 上，会掩盖真实劣化。
- 下一次按键发出时，作废已超时的计时，避免一个没有回显的按键长期占着计时器。

**正则那段必须真跑**：Go 侧只能断言源码里有没有某个字符串，测不出正则写错。第一版就把
tmux passthrough 的范围写错了（用「不含 ESC」界定，而内部转义序列的 ESC 是成对写的）。
守护测试是 `internal/server/web/enhance_query_frame_test.mjs`（用真机抓到的 48 字节帧做用例），
由 `TestEnhanceQueryFrameFilter` 调起，本机没有 node 时自动跳过。

**尚未确定的部分（下次接手请从这里继续）**：全屏 TUI 真实的打字延迟仍未测到可信数字。
合成探针进不了 TUI 的输入框（30 次按键 23 次无响应），量到的是无效样本。
早期一次针对新启动 TUI 的测量得到 P50 39ms / P95 89ms（当时机器还处于重负载），
据此推测全屏 TUI 标签页端到端应在 100ms 量级，**但这不是结论**。
可信数字只能来自装了新口径后的真实使用。

**注意别踩**：全屏 TUI 只会接管**真实存在的**智能体会话，没有沙盒模式。
用合成按键去测它，字符会落进用户正在用的会话输入框。排查时不要再这么做。

## 四、浏览器渲染：ble.sh 修完后的最大剩余杠杆

普通 shell 把远端开销归零之后，真实浏览器里再拆「回显到达」与「画面绘制完成」：

| 段 | P50 | P95 |
|---|---|---|
| 按键→回显到达（全部网络+远端） | 61.4ms | 66.4ms |
| 回显到达→画面绘制（canvas） | **69.1ms** | **109.9ms** |
| 同上（webgl + preserveDrawingBuffer） | **26.5ms** | **43.6ms** |

渲染段一度比整条链路还大。已确认**没有空间**的项（都有开/关对照）：
WebSocket 压缩（已开、零代价）、Nagle、换中转节点、QUIC、并行/异步/缓存
（一次按键回显是严格串行往返，无可拆部分）。

**采用的修法**：iframe 改 `?rendererType=webgl`，`enhance.js` 强制
`preserveDrawingBuffer: true` 保住截图。裸 WebGL 截图全黑（`nonBlackPct: 0`），
开开关后恢复且速度不丢。详见根 `AGENTS.md` 对应条目。

**勘误（2026-08-31）**：WebGL 默认已改回 canvas，因为 Corral 流式中文会把
xterm 5.4.0 图集挤爆（中文消失/花屏）。上表数字仍成立，但产品选择了正确性
而不是那 44ms。见 [TUI 乱码](2026-08-20-tui-display-corruption.md)。

无头 Chromium（SwiftShader）上的绝对值偏高，有独显的真机更好；
**canvas vs webgl 的差值**在同一浏览器同一时刻对照下可信。

## 五、CPU 拥堵：所有交互延迟的放大器

终端主机 4 核，只要 `/proc/pressure/cpu` 的 `some avg300` **超过 20%** 就在排队，
按键路径上的任何计算都会被成倍放大。网络再干净也会觉得卡。

某常驻服务曾空转吃掉约 1.5 个核（已停）。仅停掉它，
同链路回显从 P50 172ms / P95 280ms 降到 P50 87ms / P95 116ms。
**它已经 inactive，再排查不要先翻这类历史服务。** 现在的典型负载是多路
agent 进程 + 正在刷屏的全屏 TUI。

### 线上数据在哪（又核过一次）

能看到。浏览器每 5s 上报的 `perf-sample` 落在网关数据目录下的性能日志（运维自定路径）。
卡顿当下再在上游主机跑 `bash deploy/sample-ttyd-lag.sh`。

某次体感卡实测（用户反馈「还是有点卡」）：

| 段 | 当时的数 | 判读 |
|---|---|---|
| 上游主机 CPU | 4 核，load 10~11；PSI `some avg300=53~56%` | **在排队**（阈值 20%） |
| 谁在吃核 | 全屏 TUI 近半 + **多路** agent 进程 | 历史服务已 inactive |
| 上游主机→网关 | ping P50 32.0ms、抖动 0.1~0.4ms、0% 丢包；ttyd `Send-Q=0` | **网络无辜** |
| 线上回显（近 1h，`echoP50Ms`） | P50 **106ms** / P95 171ms | 干净基线是 29 / 35ms |
| 浏览器 `longTaskMs` | 全是 0 | 不是前端主线程 |

所以这次体感卡是远端 CPU 排队，不是链路。`echoP50` 不含浏览器绘制；
默认改回 canvas 那 ~44ms 绘制段是另外一笔，不在这份样本里。

## 六、复现这套测量时的两个操作坑

- **`pkill -f` / `pgrep -f` 会匹配到自己所在的那条命令行**，把执行命令的 shell 一起杀掉
  （表现为命令莫名以退出码 144 结束）。加方括号（`[t]tyd`）也救不了——只要调用命令里
  出现过目标字符串就会自匹配。**可靠做法是把启停写进一个脚本文件再执行**，
  或先用 `ss -ltnp` 拿到 PID 再按 PID kill。本次连踩三次。
- **非 root 调低进程优先级是单向门**：`renice` 调高 nice 值之后**改不回来**
  （受 `RLIMIT_NICE` 限制且无提权手段）。想用 renice 做对照实验前先想清楚，
  受影响的进程只能等各自重启才恢复默认。
