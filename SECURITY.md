# Security

ShellGate grants access to a real shell. Only invite people who are trusted to use the configured terminal account. Account-owned tabs and presets are isolated by the gateway, but ttyd processes share the upstream OS account. All allowed accounts can access every configured machine; there is no per-account machine access policy. When groups must not share files, processes or privileges, deploy separate gateway + ttyd stacks with distinct allowlists and domains, backed by separate OS accounts, containers or machines.

Local account/password sign-in is the default; passkeys are optional. Generic OIDC SSO is an optional external login: standard Authorization Code + PKCE against operator-configured Discovery/JWKS, using maintained go-oidc/Go OAuth2 libraries, with ID-token signature/issuer/audience/authorized-party/subject/expiry/nonce verification, subject-bound UserInfo, a verified email claim and an email allowlist check before minting the gateway's own session. All remote login requires a trusted HTTPS origin, with localhost as the development exception. Registration requires an operator-created, expiring, one-use invitation for an allowed email (local accounts only; SSO trusts the provider instead of invitations). The invitation stores only a hash. WebAuthn validates origin, RP ID, challenge and user verification; sessions use a separate persistent signing key, an expiry and HttpOnly cookies. Restarting during an unfinished passkey ceremony requires starting that ceremony again. Local ceremonies support one gateway instance; use the external identity adapter for multiple edges.

Passwords are stored as salted Argon2id hashes (19 MiB, two iterations, one lane), using constant-time comparisons. Passwords accept 12–128 characters without composition rules. Login errors do not disclose account existence. Password endpoints admit at most 30 requests per minute per socket peer and two concurrent hash operations per instance; behind a reverse proxy, peers may share that limit. Recovery requires a fresh operator invitation and changes the credential version, invalidating earlier cookies on their next request or WebSocket handshake. It does not forcibly terminate an already open terminal connection. There is no email delivery or public self-registration dependency.

TOTP is opt-in per account and, after confirmation, gates every primary login route. Pending challenges are opaque browser-bound cookies backed by short-lived database records, never workspace sessions. Verification uses six-digit RFC 6238 codes with a 30-second period and one adjacent step of skew; successful steps and recovery codes cannot be reused. Persistent account-level attempt limits, row locks and atomic audit prevent cross-instance replay and concurrent recovery-code consumption. Seeds are AES-GCM encrypted with account-bound additional data under the private `totp.key`; ten high-entropy recovery codes are stored only as hashes. A recent primary sign-in is required for changes; removing the factor or replacing recovery codes additionally requires a valid factor proof. Password recovery never clears TOTP. An explicit local operator reset is audited. Factor-version checks invalidate earlier cookies on the next request/handshake; already-open terminal connections remain connected. See [deployment recovery and key backups](docs/DEPLOYMENT.md#two-factor-authentication). TOTP does not provide phishing resistance, and a compromised runtime or combined database/key backup can expose seeds.

Keep ttyd unreachable except from the gateway. `X-Webauth-User` authenticates the gateway's request; it does not create or select an OS user. Browser-supplied authentication headers are stripped. Cookies and bearer credentials are removed before upstream forwarding. Proxy transports do not use environment proxies. Cross-site writes and WebSockets are rejected, request bodies are bounded and framing the workspace is prohibited.

Back up the database, session key and TOTP encryption key as sensitive data. On Unix, the directory uses mode 0700 and sensitive files mode 0600. Windows operators must restrict the data directory ACL to the service account; Unix mode bits are not a Windows access-control guarantee. Password hashes, public keys, emails, tab commands and audit metadata reside in the database; terminal screen contents are not persisted by ShellGate. Browser diagnostics are disabled by default. Enabling them can collect browser URLs and diagnostic metadata; protect and rotate that data. Do not enable diagnostics on a public demo with real accounts.

Audit records contain actor, action, target and time and commit with user mutations. They are append-only through the application, not tamper-proof against a database administrator. SQLite is the standalone default. PostgreSQL is optional; use a private service network or verified TLS when crossing a host boundary.

The initial public history is exported from a reviewed source tree without importing earlier private commits. Secret scans are preventive checks, not proof that a credential was never exposed. Rotate any real secret that was previously committed to a private or public repository.

## Dependency assessment

Go 1.26.10 is the minimum build toolchain: it fixes the reachable crypto/x509 certificate-distrust issue [GO-2026-6809](https://pkg.go.dev/vuln/GO-2026-6809) found during SSO review. Rebuild existing binaries and container images to include the fix. `govulncheck -show verbose ./...` reports GO-2026-5932 in the required `golang.org/x/crypto` module: its unmaintained OpenPGP packages have no fixed version. ShellGate imports none of those packages and has no OpenPGP feature; package and symbol scans are clean. Retain the module for WebAuthn's supported cryptography and recheck each release. See [the official advisory](https://pkg.go.dev/vuln/GO-2026-5932).

## Reporting

Please do not put credentials or exploit details in a public issue. Use private vulnerability reporting where available, or contact the repository maintainer privately. Supported security fixes apply to the latest release.
